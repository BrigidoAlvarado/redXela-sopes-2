# F9: interfaz Angular

## Organización

La aplicación usa componentes standalone y rutas en `src/app/app.routes.ts`. Las seis vistas de `pages/` son `DashboardPage`, `PedidosPage`, `InventarioPage`, `RecursosPage`, `PlanificacionPage` y `DeadlockPage`. Los estilos compartidos están en `src/styles.css`; la disposición se adapta a pantallas pequeñas y las tablas pueden desplazarse horizontalmente.

`core/models.ts` describe los contratos de F8 y convierte milisegundos simulados a una duración legible. `ApiService` centraliza la dirección `http://localhost:8080`, las peticiones HTTP, los mensajes de error y el bloqueo de solicitudes duplicadas. Las operaciones solo se confirman después de recibir una respuesta del servidor. El backend mantiene toda la lógica de inventario, planificación y sincronización.

## Datos y comunicación

`WebsocketService` mantiene una sola conexión STOMP a `ws://localhost:8080/ws`, suscrita a `/topic/estado`, con reconexión cada cinco segundos. `EstadoService` comparte mediante signals el estado del motor y los recursos. Si se pierde WebSocket, consulta estado y recursos por REST cada cinco segundos; al reconectarse vuelve a usar las instantáneas. Las operaciones REST funcionan independientemente del WebSocket.

Las vistas solicitan los datos detallados por REST cada cinco segundos mientras están activas y detienen el temporizador al salir. La comparación consulta su resultado cada 1,5 segundos únicamente mientras esté en curso y la vista esté activa. Las recepciones y la comparación iniciadas durante la sesión se recuerdan al cambiar de vista. El backend no ofrece un listado de recepciones históricas: tras recargar la página se puede consultar una recepción usando su UUID completo.

Los errores `codigo`/`mensaje` de F8 se presentan en un aviso; si el backend no responde se informa la desconexión. Las solicitudes tienen un límite de diez segundos; ante un vencimiento se pide revisar el estado antes de reintentar. Los formularios validan campos básicos, cantidades positivas y productos repetidos, y deshabilitan la operación mientras se procesa. El backend sigue realizando las validaciones definitivas.

## Inicio

Se requiere Java 21 y Node.js 24. Desde `backend/`, ejecutar `./mvnw spring-boot:run`. Desde `frontend/`, ejecutar `npm ci` y `npm start`; abrir `http://127.0.0.1:4200`. Las direcciones de desarrollo están centralizadas en `core/api.service.ts`. Para verificar el frontend se utilizan `npm test` y `npm run build`.

## Demostración de deadlock

1. Iniciar el motor en el panel general.
2. Registrar un cliente y dos pedidos distintos de mercancía general sin existencias suficientes.
3. En **Deadlock**, seleccionar ambos pedidos y preparar la demostración. El backend puede indicar `ESPERANDO_DESPACHOS`.
4. En **Inventario**, registrar una recepción suficiente y esperar su estado `ALMACENADA`.
5. Volver a **Deadlock**. Cuando el backend detecte la espera circular, se muestran C01, S01, los propietarios y los recursos esperados.
6. Seleccionar qué operación continúa. La pantalla muestra `RECUPERANDO` y solo presenta el éxito cuando el backend informa `RESUELTA`. Los pedidos y recursos pueden observarse en sus respectivas vistas.

La comparación de políticas muestra el escenario y resultados del backend. El resultado es una muestra concurrente; no se presenta una política como ganadora absoluta. La aplicación y el historial operativo permanecen en memoria: no hay persistencia ni autenticación en esta fase.
