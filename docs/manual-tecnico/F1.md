# F1 — Configuración y dominio

## Alcance

Esta fase implementa la base Java 21 / Spring Boot 4.1.2 / Maven y Angular 21.2.0, más los modelos de cliente, pedido, producto, tipo de mercancía, servicio y necesidades de recursos. Incluye creación y consulta en memoria y pruebas del código de esta fase.

No implementa F2: no existe reloj, ciclo de simulación, generador ni tareas permanentes. Tampoco se adelantan la API de negocio, el inventario o la interfaz operativa. El contexto de Spring conecta servicios Java independientes del framework y Angular arranca como aplicación standalone.

## Decisiones de implementación

- Se usan records y colecciones defensivas para datos inmutables. No hay setters que permitan saltarse validaciones o alterar pedidos desde otro hilo.
- `CatalogoProductos` conserva diez productos, dos por cada uno de los cinco tipos aprobados. El catálogo no permite escrituras y rechaza códigos inexistentes.
- `TipoMercancia` declara por etapa las necesidades exactas de la propuesta: General, Frágil, Pesado, Voluminoso y Electrónica paletizada. El servicio contratado no cambia esas necesidades.
- `TipoRecurso` declara las capacidades obligatorias y genera identificadores físicos válidos, entre ellos C01 y S01. No administra permisos ni dice que un recurso esté ocupado en esta fase.
- `ClienteService` utiliza una sección crítica corta para mantener consistentes los índices por ID y correo. No llama a otro módulo ni hace I/O dentro de esa sección.
- El correo se recorta y normaliza a minúsculas con `Locale.ROOT`, como regla de identidad del simulador. Se valida formato básico, sin verificar la existencia del buzón ni implementar autenticación.
- `PedidoService` resuelve clientes registrados y productos canónicos. Mantiene pedidos inmutables en `ConcurrentHashMap` y utiliza `AtomicLong` para el desempate por secuencia. La secuencia puede tener huecos después de una entrada inválida; no representa tiempo ni exige consecutividad.
- Los IDs de cliente y pedido son UUID generados por el servidor, no elegidos por el consumidor. El servicio de pedidos comprueba colisiones antes de registrar.
- Un pedido guarda el cliente y el nivel contratado. Puede contratar un nivel distinto del preferido sin alterar al cliente ni a sus productos.
- El código de producto se normaliza a mayúsculas. Una solicitud con el mismo producto repetido se rechaza, en vez de combinar cantidades de forma implícita.
- Cantidades por línea y volumen por unidad son enteros positivos. Las sumas de unidades y los productos de volumen utilizan `long` para evitar desbordar un `int` válido.
- El pedido inicial tiene estado `CREADO`. Los demás valores de `EstadoPedido` constituyen vocabulario para fases posteriores; F1 no permite fingir procesamiento cambiando un estado.
- `PlanTrabajo` agrupa unidades por tipo y recorre retiro, empaque, calidad y despacho en ese orden. Omite calidad cuando no aplica. Cada combinación etapa/tipo aparece una vez aunque haya varios productos del mismo tipo.
- Cada `PasoTrabajo` tiene posición estable y necesidades inmutables. Todavía no ejecuta nada. Las fases de concurrencia agregarán un seguimiento/checkpoint por pedido e intento separado de esta definición, de modo que reencolar despacho no reconstruya ni repita retiro o empaque.
- No se añaden abstracciones temporales ni un reloj alternativo. `Duration` solo expresa objetivos del dominio. Las duraciones de ejecución y su avance se incorporarán con el único reloj simulado en F2.

## Validaciones

Los constructores y servicios rechazan entradas inválidas mediante `IllegalArgumentException` con mensajes descriptivos. Es una excepción de entrada de dominio; su traducción a errores REST corresponde a la fase de API.

Se comprueban campos obligatorios, textos vacíos o demasiado largos, formato de correo/código, nivel de servicio fuera de 1–5, cantidades no positivas, requisitos por encima de la capacidad, pedido vacío, líneas nulas, productos repetidos, cliente desconocido y productos que no pertenecen al catálogo.

No se valida stock ni disponibilidad de ubicaciones: aún no hay inventario. Un pedido grande puede ser válido como solicitud aunque deba esperar reposiciones en fases posteriores.

## Semántica temporal acordada

Estas definiciones quedan documentadas ahora; **F1 todavía no calcula métricas temporales**:

1. **Espera para el nivel de servicio:** intervalo desde que el backend acepta el pedido hasta que comienza su primer trabajo físico efectivo, en tiempo simulado. Incluye espera inicial por inventario, planificación y recursos. Crear la cuenta, enviar el formulario, reservar stock o asignar recursos sin comenzar trabajo no cuentan como primera atención.
2. **Objetivos:** Exprés tiene un umbral inicial de 30 segundos simulados, decisión de diseño para concretar “casi instantáneo”. Los otros niveles conservan 10, 30, 60 y 120 minutos del enunciado. El caso Exprés deberá poder configurarse con el reloj/motor; en F1 solo existe el valor inicial del dominio.
3. **Espera acumulada:** suma de intervalos sin trabajo efectivo desde la aceptación, antes y después del primer inicio, desglosados en inventario, planificación, recursos y recuperación. El tiempo en deadlock se cuenta como espera aunque una operación retenga equipo; se evita contar dos veces un mismo intervalo.
4. **Procesamiento:** suma de intervalos de trabajo efectivo; los reintentos y el trabajo desperdiciado se identificarán de forma explícita.
5. **Pausa:** no avanza el reloj y no incrementa ninguna de esas duraciones. Toda medición funcional utiliza tiempo simulado; tiempo real solo sirve para límites de infraestructura y de pruebas.
6. **Aging:** usará el tiempo elegible acumulado de planificación y recursos definido en la propuesta, conservándolo entre reintentos. No es sinónimo de espera de SLA ni de toda la espera acumulada.

La expresión de la tabla del enunciado se interpreta como tiempo hasta primera atención. La espera acumulada y el retorno se mostrarán adicionalmente para no ocultar bloqueos posteriores ni aparentar cumplimiento completo solo por iniciar rápido.

## Pruebas incluidas

- Contexto Spring: resolución de beans y creación de un pedido válido.
- Catálogo: IDs únicos, cinco tipos, inmutabilidad, normalización y códigos desconocidos.
- Recursos descriptivos: capacidades obligatorias, identificadores, perfiles distintos, solicitudes posibles y carga/escáner compartidos en despacho.
- Servicios: objetivos 30 segundos / 10 / 30 / 60 / 120 minutos y rechazo de niveles inválidos.
- Clientes: campos obligatorios, correos inválidos, normalización y duplicados.
- Concurrencia de clientes: 64 intentos para el mismo correo aceptan exactamente uno; 64 registros distintos se conservan y se consultan correctamente.
- Pedidos: cantidades, líneas vacías/nulas/duplicadas, productos/clientes inexistentes, independencia entre servicio preferido y contratado, copias defensivas y aritmética mayor que `Integer.MAX_VALUE`.
- Concurrencia de pedidos: 128 creaciones conservadas con secuencias e IDs únicos.
- Rutas: agrupación por tipo, orden de etapas, posiciones estables, calidad opcional y aumento de carga por unidades sin multiplicar equipo necesario.
- Angular: arranque y renderizado de la aplicación raíz.

Las pruebas concurrentes usan ocho trabajadores, `CountDownLatch` y límites en `Future.get` para detectar fallos. No usan `Thread.sleep()`. Todos los ejecutores de prueba se cierran en `finally`.
